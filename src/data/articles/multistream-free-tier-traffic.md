## 用免費方案跑一個會一直去問 YouTube 的網站

MultiStream Hub 要知道收藏的頻道有沒有在直播，開台週表上線之後又要追幾百位 VTuber 的排程，等於整天都在問 YouTube「這個人開台了沒」。網站跑在免費方案上：前端跟 API 在 Cloudflare Pages／Workers，每次請求的 CPU 時間只有 10ms；資料庫跟排程在 Supabase，資料庫上限 0.5GB，Edge Function 記憶體 256MB、單次執行超過 2 秒會被直接砍掉；再加上 YouTube Data API 每天有配額。

九月底到十月初這幾個上限我幾乎全撞過一輪。下面照時間整理遇到的問題跟後來怎麼降下來，如果你也在用免費方案跑類似的東西，應該有幾個坑可以先避開。

## 每個人都自己去問一次

我判斷 YouTube 頻道有沒有開台，是去抓頻道的 `/live` 頁面來看，這支端點我叫它 live-og。9 月 23 日看數據才發現，它一個月被打了 132 萬次，佔全站請求的 78%。每次都要抓大約 1.6MB 的 YouTube 頁面來解析，CPU 要 8 到 11ms，剛好卡在 10ms 的上限上下，結果出現 1.12 萬次 503。快取命中率只有 0.92%，也就是幾乎每次都是重新抓。

問題在於同一個頻道，每個收藏它的使用者都會自己去問一次。後來改了三件事：

- **邊緣快取**：同一個頻道 3 分鐘內只抓一次 YouTube，抓失敗的結果只留 60 秒。
- **共享查詢結果**：第一個查到的人把結果寫進資料庫的共享表，其他人直接讀資料庫，不用再打一次端點。前端每輪先批次讀共享表，3 分鐘內的資料直接用，只有沒資料或過期的頻道才去打端點。
- **只給自己的網站用**：查記錄的時候發現 30 天裡有 2.6 萬次是有人直接用 curl 打這支端點，因為 CORS 設的是 `*`，等於我免費提供了一個開台偵測 API 給別人用。改成只接受本站來的請求。

共享表只開放讀取，寫入只有伺服器能做。這張表裡有影片連結，如果讓人隨便寫，等於讓人塞釣魚連結進來。

## 把被限流當成頻道壞掉

開台週表的後端是排程去掃頻道的 RSS 找新影片。9 月 30 日在本機測的時候發現，YouTube 對大量 RSS 請求會限流，回很快的 404 或 500；我的程式把這當成「這個頻道壞了」，連續失敗 3 次就改用 YouTube API 的 playlistItems 去查，而且沒有設上限。結果一天燒掉大約 6,000 單位的配額。

修法是把資料來源的順序整個反過來：

- 開台判斷以 live-og 為主，它不花配額。
- RSS 只拿來找新影片。同一輪如果超過一半都失敗，就當成整批被限流，直接停手，而且不算在頻道頭上。拿掉 playlistItems 這條退路，並行數也從 25 降到 8。
- API 放最後，只查 RSS 找到的新影片，每輪最多 4 次，每天上限 2,000 單位。

改完之後排程每輪大約只花 1 單位配額。這次也順便拿掉了觀看人數的顯示，直播改成照開台時間排序。

這次學到的是：外部服務回錯誤的時候，要先分清楚是「對方壞了」還是「你被擋了」。被擋的時候換一條更貴的路去重試，只會讓事情更糟。

## 一個頁面明明只需要兩小段，卻每次都讀完整頁

10 月 1 日再看正式站，7 天內還是有 6,148 次超過 CPU 時間限制。我回頭看 live-og 在做什麼：每次把整個 YouTube 頁面（1.5～1.8MB）讀完、解碼，再對整頁跑大約 10 次 regex。更慘的是 watch 頁根本沒有 og:image，那兩條找 og:image 的 regex 每次都要掃完整頁才失敗。

其實判斷開台只需要兩小段資料。所以改成串流讀取：

- 離線的頻道頁，讀完前 64KB 就取消下載。
- watch 頁讀到 `ytInitialPlayerResponse` 那段 script 結束就取消。
- regex 只在這兩小段裡跑。

拿 13 個真實頁面（直播 5、待機 4、離線 4）比對，輸出跟改版前完全一樣。CPU 平均從 3.37ms 降到 1.08ms，離線頁降了 90%，直播跟待機室降了 63%；離線頁的讀取量從 1.57MB 降到 96KB。

同一段時間還踩到一個記憶體的坑。Supabase Edge Function 記憶體上限 256MB，跑到大約 81～90 個頻道就爆掉。查下去才發現是 V8 的行為：從大字串切出來的子字串（13 個字元以上），會把整個原始字串一起留在記憶體裡。我只是想留下標題，卻把整頁 HTML 一起留到這一輪結束，60 頁在 GC 之後還佔 171.7MB。把要留的字串複製成獨立的字串之後，60 頁的記憶體高峰從 215～230MB 降到 26～28MB。

## 一個人佔掉一半的流量

10 月 4 日，Pages 24 小時內又出現 8,028 次超過 CPU 時間限制。這次的主因很意外：有一位使用者收藏了大約 150 個 YouTube 頻道。我原本的節流只看單一頻道，沒有限制每個人的總量，所以這位使用者的瀏覽器每 2 秒就打一次端點，一輪接一輪不停，7 天大約 7.2 萬次，佔全站一半。共享表只接受 3 分鐘內的資料，可是週表排程大概 10 分鐘才更新一次，所以共享表的資料常常被當成過期，又回頭去打端點。

這次的修法是幫每個人設總量：

- 每輪最多打 10 次端點，最久沒查的先查；同一個分頁同時只跑一輪，整輪超過 2 分鐘就放棄。
- 查失敗的頻道 5 分鐘內不重試。
- 手動重新整理 3 分鐘內只會生效一次，跨分頁也算，冷卻中會顯示還要等幾秒。
- 共享表的新鮮度配合排程放寬到 22 分鐘，正在直播的頻道改成每小時重新確認一次。
- 週表的排程也降頻：直播狀態每 20 分鐘一輪，重的工作每小時一輪。

代價就是開台跟下播的反映會慢一點。開台通常要幾分鐘到二十幾分鐘才會出現在週表上，下播最晚要一個半小時左右才會移到「剛結束」。我覺得對週表來說這個延遲可以接受，總比整個網站因為超過額度掛掉好。

## 資料庫也會偷偷滿出來

10 月 1 日發現資料庫用到 0.527GB，超過免費方案的 0.5GB。佔空間的不是我的資料，是排程本身的記錄：pg_net 的 HTTP 回應表堆了 348MB，pg_cron 的執行記錄 14 天前的就有 77,126 筆。清掉這些、刪掉一個跟唯一索引重複的索引之後，從 488MB 降到 84MB。後來加了一個每天自動清 14 天前執行記錄的排程，免得再滿一次。

## 如果你也在用免費方案

整理一下這輪下來我會先檢查的事：

- 同一份資料如果很多人都會查，先查一次、存起來給大家共用，不要讓每個人各自去問外部服務。
- 外部服務回錯誤的時候，先判斷是不是被限流，被限流就停手，不要換更貴的方法重試。
- 只需要頁面的一小段，就用串流讀取，讀到就停，不要整頁讀完再找。
- 節流除了限制單一項目，也要限制每個使用者的總量，不然一個重度使用者就能把額度吃光。
- 排程跟資料庫擴充（像 pg_cron、pg_net）自己也會產生資料，記得定期清。
- 端點不要開 `CORS: *`，除非你真的想讓全世界免費用。

這些數字都是在 MultiStream Hub 正式站跟本機實測出來的，換了平台或流量規模不一定一樣，但思路應該通用。
